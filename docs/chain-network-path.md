# مسار البث والمراقبة — 2026-10-31

## ما نُفّذ

هذه إضافة لمسار الشبكة الخاص، وليست إعلان إطلاق مالي أو خدمة تعمل تلقائيًا الآن.

### البث

`chain-broadcast.ts` يوفر محولًا للشبكتين يُحقن في `dispatchSavedPayout` **بعد تسجيل مطالبة الإرسال الدائمة**:

- BEP20: يراجع التوقيع وTXID والشبكة 56 وعقد USDT ونداء transfer الدقيق وقيمة native الصفرية، يثبت eth_chainId، ثم يرسل نفس البايتات المحفوظة عبر eth_sendRawTransaction.
- TRC20: يراجع hash/protobuf والتوقيع المستعاد والمرسل والعقد ونداء transfer وعدم إرفاق قيمة native وعدم انتهاء الصلاحية، يتحقق من genesis ID مثبت في الإعداد، ثم يرسل JSON المحفوظ دون إعادة توقيع أو بناء معاملة جديدة.
- لا retry في المحول؛ كل رفض أو duplicate/already-known أو nonce conflict أو مهلة أو رد غير مطابق يبقى نتيجة غير محسومة للمطالبة الدائمة. لا يدل ACK على إدراج أو نجاح.
- لا يُعاد توليد nonce أو تجديد توقيع TRON المنتهي تلقائيًا. التوقيع المنتهي قد يكون قد نُفّذ قبل انتهائه، ولذلك تستمر مراقبته ولا يُرد المال لمجرد انتهاء الوقت.

### النقل

`chain-http.ts` يفرض HTTPS وإعدادات مشغّل فقط، رفض credentials داخل authority والعناوين المحلية/IP المباشرة، عدم اتباع التحويلات، مهلات تشمل القراءة المتدفقة حتى مع fetch يتجاهل AbortSignal، حد حجم الرد، JSON/UTF-8 صالح، وإخفاء عنوان المزود ومفاتيح API وأجسام أخطائه. ليس DNS pinning أو حماية DNS rebinding كاملة؛ لا تُقبل إعدادات endpoint من العملاء مطلقًا.

### مراقبة TRON

`tron-receipt-observer.ts` أضاف مراقبًا فعلي البروتوكول لواجهات walletsolidity:

1. مطابقة genesis المثبت من مصدر مستقل للشبكة الرئيسية، وليس عينة الاختبار.
2. transaction info يثبت ID والنجاح؛ لا تعتبر الاستجابة الفارغة فشلًا نهائيًا.
3. كتلة solidified تغطي ارتفاع المعاملة.
4. تطابق ارتفاع الكتلة مع blockID ووجود TXID مرة واحدة ونجاح التنفيذ داخلها.
5. تطبيع Transfer وربطه بالعقد والمستفيد والكمية عبر المحقق الحالي.
6. قراءة ثانية لنفس الكتلة قبل التسوية، ورفض تغيّر hash.

لا يستبدل latest بـsolid، ولا يتسامح مع نقص حقول نجاح أساسية. قد يتطلب المزود تكييفًا موثقًا إذا كانت استجابته لا تعرض الحقول المطلوبة؛ لا تُخفف هذه الشروط لتجاوز فحص فاشل. الدليل من RPC موثوق، وليس برهان inclusion تشفيريًا أو عقدة يتم التحقق منها محليًا.

### ربط الدليل بالتسوية

- `outbox-observer.ts`: يبحث ضمن 128 log كحد أقصى عن **Transfer واحد فقط** يطابق المرسل والمستفيد والعقد والكمية تمامًا؛ يستخدم logIndex الفعلي لـBSC، ثم يستدعي مراقب النهائية مرة واحدة. يمنع حلقة طلبات RPC لكل log غير مطابق.
- BEP20 يستخدم مراقب chain56/finalized-tag/inclusion وإعادة قراءة الكتلة الموجود مسبقًا.
- `payout-network-worker.ts`: يربط المخرج المحفوظ → dispatch الدائم عند تفعيله → مراقب الشبكة → confirmPayout → القيد المزدوج/تسوية المصروف القائمة. المراقبة تستمر حتى بعد خطأ dispatch لمعالجة محاولة سابقة غير محسومة. لا يأخذ receipt أو مبلغًا أو مستفيدًا من المستخدم.
- `sweep-network-observer.ts`: يقرأ مصدر الإيداع والمخرج الموقّع، يستخرج المبلغ من calldata المحفوظة (لا يوجد amountBaseUnits في جدول sweeps)، ويربط المراقبة بـconfirmTronSweep/confirmBep20Sweep. لا يحرر المصدر إلا بعد التحقق الكامل من التوقيع والتنفيذ النهائي.
- `outbox-network-runtime.ts`: تركيب production خاص مع أعلام مستقلة ومعطلة افتراضيًا؛ لا يستورد أو يحمّل مفاتيح توقيع.

## ما اختُبر فعليًا

- `test:chain-network`: معاملات موقّعة محليًا بمفاتيح fixtures علنية؛ نفس البايتات في طلب البث؛ رفض شبكة خاطئة وhash مخالف؛ انتهاء/إلغاء الطلب؛ fetch معلّق وbody معلّق وحجم زائد؛ حجب مسار broadcast في عميل القراءة؛ TRON solidity/inclusion/نتيجة فاشلة/reorg؛ انتقاء Transfer الفريد على الشبكتين ورفض التكرار أو اختلاف المبلغ.
- `test:payout-outbox`: المحول الحقيقي مع HTTP اصطناعي، مطالبة DB مثبتة قبل استدعاء eth_sendRawTransaction، انقطاع وإعادة محاولة دون إرسال ثانٍ؛ ربط كل مراقب بالتسوية على PGlite، بما فيه TRON بتوقيع قديم، وحالات HELD وrollback دون تحرير المال.
- `test:sweep-outbox`: مراقبة الشبكتين مربوطة بإثباتات وتوقيعات حقيقية محلية وسجل تأكيد PGlite، ثم إعادة المراقبة بلا تكرار وتحرير المصدر فقط بعد النهائية.

نجح npm test كاملًا وnpm run build بعد آخر تعديل، وnpm audit بصفر ثغرات معروفة. لم تُستخدم أسرار إنتاج أو معاملات شبكة حقيقية أو توكنات مدفوعة في هذه الاختبارات.

## حدود التشغيل التي لا تزال مفتوحة

1. المحول جاهز للحقن في مسار سحب ذي موافقة موارد وميزانية دائمة؛ **لا يوجد مسار بث sweeps ذو موافقة موارد/ميزانية دائمة مكافئ بعد**. مراقبة sweeps منفذة، ولا يجوز تمرير محول البث مباشرةً من endpoint لتجاوز هذا النقص.
2. لا توجد جدولة production أو قائمة عمل ذات checkpoint/lease محفوظة لهذه الإضافة؛ الدوال تعالج ID واحدًا من outbox الدائم. ليس هذا مراقب اكتشاف إيداعات أو مسح كتل مستمرًا. يجب معالجة العدالة بين العناصر العالقة وإعادة التشغيل/المهلات عند تركيب الجدولة.
3. يلزم endpoint موثوق لكل شبكة، دعم BSC finalized، وgenesis TRON مستقل التحقق، ثم فحص قراءة حي دون توقيع. لم يُنفذ ذلك هنا.
4. دور اتصال التطبيق الحالي محجوب عن المال؛ يلزم تصميم سلطة عامل مالي ضيقة ومراجعتها، وليس GRANT ALL على runtime.
5. رفض/إلغاء نهائي للمعاملة أو تعارض nonce لا يتيح refund تلقائيًا. لا يوجد رصد يعكس التسوية عند reorg بعد نهائية سبق اعتمادها؛ يحتاج ذلك إنذارًا وإيقافًا ومسار حادث مستقلًا.
6. شراء/توصيل/تسوية الطاقة والتسعير وتجارب التشغيل المالي المأذونة تبقى بوابات منفصلة. لا تعبئة مزود الطاقة ولا وجود محول بث يُكملها.

الأعلام الموثقة في `.env.example` لا تُفعّل تلقائيًا، ولا يوجد route عام جديد. لا تُفعّل `SIRO_OUTBOX_WORKER_ENABLED` أو `SIRO_BROADCAST_ENABLED` أو التوقيع لمجرد نجاح اختبارات fixtures. قرار NO-GO المالي باقٍ حتى إغلاق هذه الحدود.
