## الخلاصة التنفيذية

لم يُفحص الموقع المنشور مباشرة؛ اتصالات البيئة الخارجية مقيّدة. لم تُقرأ أسرار الإنتاج أو تُعدّل إعداداته، ولم تُشغّل عمليات توقيع أو بث أو شراء طاقة أو ترحيلات مالية. لم يُستخدم Strix أو ZAP أو CodeQL؛ لا تُنسب إليها أي نتيجة في هذا التقرير.

## فرز نتائج Semgrep

العدد الخام: **628 تنبيهًا**. وصف الأداة لها بأنها blocking لا يساوي خطورة أمنية أو إثبات استغلال.

- 616 تنبيه تدويل/تنسيق مفاتيح i18next: ليست ثغرات أمنية مثبتة، والمشروع لا يلزم باستخدام i18next.
- تنبيهان لتعبير منتظم ديناميكي في تحقق إيصالات TRON/BSC: طول التعبير يأتي من ثوابت داخلية؛ لم يُثبت وصول مهاجم إلى تركيب التعبير أو ReDoS عبرهما.
- تنبيه HTML في قالب البريد: الرمز محصور في ستة أرقام، وبقية المتغيرات نصوص مؤلَّفة ثابتة؛ لم يُثبت إدخال HTML من المستخدم في الموضع المنبَّه إليه.
- أربعة تنبيهات JSON.stringify: أحدها تسلسل بيانات فحص صورة، والبقية بناء بصمات عملية/معاملة من بنى محددة. لم يُثبت اختلاف ترتيب مفاتيح يسمح بتجاوز توقيع أو موافقة؛ تظل اختبارات ربط الهوية المالية ضرورية.
- خمسة تنبيهات صحة/توافق أخرى: ثلاثة تعبيرات شرطية متكافئة، replaceAll في عامل Cloudflare، وتحذير قالب نصي في CSS البريد؛ ليست ثغرات مثبتة. تنبيه التكافؤ في حساب قيمة الإيداع لا يطابق المصدر الذي يختار فعلًا 6 أو 18 منزلة؛ لا يُعتمد تصنيف الأداة دون مراجعة.

## فرز نتائج فحص الأسرار

مرشحات النسخة الحالية شملت عناوين عامة، معرّف حدث Transfer، أسماء حقول، بيانات اعتماد localhost نموذجية في `.env.example`، وقيم اختبار اصطناعية. لم يُثبت مفتاح إنتاج متسرّب ضمنها.

في التاريخ، كان **1589 من 1706** مرشحات في حقول `integrity` الخاصة بـpackage-lock؛ تحقّق آلي إضافي أثبت أن جميع مرشحات ذلك الملف داخل حقول تجزئة الحزم. بقية أصناف المرشحات تتكرر في الأمثلة والاختبارات والعناوين والكلمات المفتاحية نفسها. هذا لا يضمن عدم وجود سر بصيغة لا تتعرف عليها الأداة، ولا يغطي فروعًا أخرى أو كائنات Git غير القابلة للوصول من HEAD أو سجلات منصات النشر.

تعذّر تشغيل Gitleaks: رابط أصول إصدار GitHub يُحوّل إلى مضيف محظور بالبيئة. استُخدم detect-secrets بديلًا، ولم يُدّع نجاح Gitleaks. تقارير الفحص لا تحتوي القيم السرية الخام؛ لم يُجرَ تحقق حي من مفاتيح مشتبه بها.

## الملاحظات المفتوحة

### A. غياب حماية تأطير صريحة في ردود التطبيق المحلية — أولوية متوسطة، يحتاج تحقق إنتاج

الملاحظة مثبتة محليًا: لا `X-Frame-Options` ولا `Content-Security-Policy: frame-ancestors` في الردود المفحوصة، ويؤكد إعداد Next غيابها. قد يسمح ذلك بالتأطير والخداع بالنقر بحسب سلوك المتصفح وحالة تسجيل الدخول. لم يُنفّذ إثبات خداع بالنقر على حساب حقيقي. كوكي SameSite=Strict يقلل بعض السيناريوهات لكنه ليس بديلًا شاملًا لحماية التأطير.

التوصية: حماية تأطير صريحة في الإنتاج، بعد ضبط الفرق بين الإنتاج والمعاينة المضمّنة في Arena حتى لا تتعطل المعاينة. لم تُضف سياسة عمياء قد تكسر بيئة العرض.

### B. لا توجد CSP شاملة — تحسين دفاعي، وليس إثبات XSS

لا توجد سياسة CSP في الرد المحلي. لم تُثبت ثغرة XSS جديدة بهذا الفحص. ينبغي تصميم سياسة nonce مناسبة لـNext، وتجربتها أولًا بوضع Report-Only، ثم الإنفاذ بعد حصر المصادر. لا يكفي وضع سياسة تسمح بكل المصادر أو unsafe-inline ثم وصفها حماية كاملة.

### C. كشف وجود حساب من مسار إنشاء الحساب — ملاحظة خصوصية في الشيفرة

في `lib/email-auth.ts` تختلف استجابة signup للبريد الموجود عن الاستجابة للبريد الجديد عند توفر البريد وقاعدة البيانات؛ يمكن أن يتيح ذلك استنتاج وجود حساب. توجد حدود طلبات عامة ولكل بريد لكنها لا تلغي اختلاف الاستجابة. لم يُجرَ تعداد لبريد حقيقي، ولم يُختبر هذا الفرع حيًا مع مزود البريد.

التوصية: استجابة خارجية موحّدة لا تكشف وجود الحساب، مع تصميم تجربة إعادة المحاولة وإرسال البريد بعناية. تغييرات الرسائل وحدها لا تضمن تساوي التوقيت.

### D. حدود حجم الطلب ومعدل المرور — يلزم تحقق البنية المنشورة

رفع الهوية لديه حد جسم صريح، وتسجيل الدخول لديه حصص بريد دائمة. لا يثبت ذلك وجود حدود IP/عالمية لكل API أو حد صغير مناسب لكل JSON. طلبات JSON في عدة مسارات تعتمد على request.json دون قارئ محدود خاص بالمسار. لا يُثبت هذا وحده قابلية إسقاط الخدمة؛ يلزم قياس حدود منصة الاستضافة والجدار الناري والحجم والتزامن في بيئة اختبار.

### E. HSTS وإعدادات الحافة — لم تُتحقق

HSTS غير موجود في الخادم المحلي عبر HTTP. لا تُصنَّف هذه الحقيقة وحدها ثغرة إنتاج؛ قد تضيفه حافة الاستضافة. يلزم فحص HTTPS الفعلي وTLS وHSTS والنطاقات وتحويل HTTP إلى HTTPS في البيئة المنشورة.

## ما أثبتته اختبارات HTTP وما لم تثبته

نجحت الاختبارات المحلية في رفض الطلبات غير المصادق عليها للهوية والجلسات وأحداث الحماية، ورفض أصول غير موثوقة ورموز موافقة مختلقة، وإعادة توجيه الصفحات الخاصة لتسجيل الدخول، ومنع تنفيذ مسارات المال القديمة. فُحصت الاستجابات دون أي اتصال بقاعدة إنتاج أو بريد أو سلسلة بلوكشين. بيئة الخادم أُنشئت بمتغيرات نظيفة، والتوقيع وقراءات RPC وPasskey المالي معطلة.

هذه **اختبارات HTTP موجّهة وليست زحف DAST شاملًا**. نجاحها لا يثبت غياب IDOR بين حسابين مسجلين؛ لا توجد هنا جلسات حقيقية لحسابي اختبار وقاعدة PostgreSQL مستقلة. كما لا يثبت اختبار النصوص أو المكونات خلو الواجهات من XSS في المتصفح.

## موانع الإطلاق المالي — باقية

راجع أيضًا `docs/deep-security-review.md` و`docs/financial-launch-status.md`:

1. لم يُنفّذ تحقق الربط التشفيري لمفاتيح الإنتاج بعناوين المحافظ الفعلية.
2. لا يزال مسار شراء الطاقة المدفوع والتسليم وتسوية الطلب المجهول والميزانية المشتركة قبل الشراء غير مكتمل.
3. يلزم تشغيل موثوق لمراقبي الشبكات والتسعير والمحاكاة والنقل والجدولة.
4. يلزم استكمال استرداد الحالات المجهولة/الفاشلة وإعادة التنظيم وإدارة nonce والمصروفات المشتركة.
5. ترحيلات المال المعدّة لم تُطبّق على الإنتاج في هذه الجولة.
6. اختبارات PGlite المتسلسلة لا تعادل اختبار سباقات بجلستين مستقلتين في PostgreSQL حقيقي.
7. لم تُختبر WebAuthn فعليًا على iPhone أو استعادة الحساب والأجهزة بمتصفح حقيقي.
8. لم يُنفّذ اختبار بأموال فعلية؛ ذلك يحتاج تفويضًا منفصلًا وضوابط تشغيل.

## الخطوة اللازمة لاستكمال تغطية الفحص

إنشاء بيئة staging مع PostgreSQL منفصل وحسابي عميل وحساب مراجعة وبيانات وهمية، دون أسرار أو مفاتيح محافظ إنتاج. ثم اختبار صلاحيات كل دور، وDAST مصادَق عليه باستخدام ZAP، ومتصفح حقيقي، وسباقات وتزامن، وفحص إعدادات HTTPS والحافة. يبقى توقيع الإنتاج معطّلًا حتى إغلاق موانع الإطلاق.

**التقييم النهائي:** نتائج الاختبارات الحالية ناجحة، ولا توجد ثغرة جديدة عالية/حرجة مثبتة في نطاق هذه الجولة؛ توجد ملاحظات مفتوحة وتغطية غير مكتملة تمنع وصف الموقع بأنه آمن بالكامل أو جاهز ماليًا.

## تحديث المعالجة — 2026-10-31

الملاحظات أعلاه تصف النسخة المفحوصة الأصلية. جرت بعدها المعالجات التالية في الفرع، دون نشر إنتاجي صريح:

- أضيف Proxy لسياسة CSP فعلية لكل صفحة، مع nonce جديد لكل طلب و`strict-dynamic` ومنع object وbase وتقييد مصادر الاتصال والصور والعمال. فُرض العرض الديناميكي كي لا تُخزّن صفحات ذات nonce قديم. تبقى inline styles مسموحة لتوافق تصميم React؛ لا يُسمح بـinline scripts غير الموثقة بالـnonce. بيئة development فقط تسمح بـunsafe-eval.
- إنتاج Vercel (`VERCEL_ENV=production`) يمنع التأطير باستخدام frame-ancestors none وX-Frame-Options DENY، ويضيف HSTS لمدة سنة دون includeSubDomains أو preload حتى لا تُفرض سياسة على نطاقات غير مدققة. المعاينة غير الإنتاجية تبقى قابلة للتضمين في Arena ولا يُستنتج وضع الإنتاج من Host يرسله العميل.
- استجابة signup للبريد الموجود أصبحت تطابق البريد الجديد في الحالة والبنية، مع نفس عمل scrypt ومسار إرسال البريد وحدود الطلبات. لا يُنشأ للبريد الموجود تحدٍّ قابل للاستخدام، ولا يُحذف تحدّيه الحقيقي، ولا تتغير كلمة مروره. قد يصل بريد رمز غير قابل للاستخدام عند محاولة إعادة التسجيل؛ معرفة الرمز لا تنشئ جلسة لحساب موجود. لا نزعم انعدام فروق التوقيت إحصائيًا في الشبكة أو قاعدة البيانات.
- استُبدلت قراءة JSON غير المحدودة في جميع مسارات API العامة المستهلكة لـJSON بقارئ يعدّ البايتات الفعلية، بما فيها chunked، بحد 16KiB ومهلة قراءة خمس ثوانٍ. Passkey له حد 64KiB لاستيعاب إثبات الجهاز. رفع الهوية يحتفظ بقارئه المحدود المنفصل. الأخطاء تعود بصيغة عامة دون كشف الجسم.
- أضيف `test:http-hardening` إلى الاختبارات الكاملة: أحجام فعلية ومعلنة، stream متجزئ، جسم متوقف، JSON تالف، nonce مختلف لكل طلب، وسياسة الإنتاج مقابل المعاينة. نجحت الاختبارات الكاملة والبناء واختبارات HTTP المحلية. تحقق إضافي في HTML المبني أثبت وجود nonce مطابق للسياسة في جميع وسوم script الاثني عشر لصفحة auth.

**ما لم يُغلق:** تفعيل/قياس WAF وحصص IP موزعة لكل API، وفحص TLS وHTTPS على النطاق المنشور، واختبار CSP بمتصفح حقيقي وجميع رحلات المستخدم. حد حجم JSON ليس بديلًا عن rate limiting؛ حصص البريد الدائمة الحالية باقية ولا تعادل حماية DDoS لكل الموقع. موانع الإطلاق المالي باقية كما هي. لا يعني نجاح هذه المعالجة أنها مطبّقة بالفعل على نشر الإنتاج القديم.
