## 1. Polling سريع حتى مع نجاح Ably — مثبت باختبار

الدليل: [app.js L837–930](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/app.js#L837-L930).

- `startRealtimeStream()` يستخدم Ably عند توفره. لكن `currentPollInterval()` لا يفحص حالة Ably مطلقًا؛ يفحص فقط `realtimeEventSource.readyState === OPEN`.
- لذلك اتصال Ably الناجح لا ينقل المؤقتين من 15 ثانية إلى 60 ثانية. في وضع التطبيق المثبت standalone يعود `startRealtimeStream()` قبل تشغيل Ably/SSE، بينما polling يبقى قائمًا.
- المؤقتان يجلبان الإشعارات ويستدعيان `loadUserProfile()` حتى دون تغيير بيانات.
- حساب توضيحي، وليس قياس زيارات: مؤقتان كل15ثانية يساويان8 دورات طلب في الدقيقة، أو480 في ساعة تبويب ظاهر واحد، قبل التحديثات التابعة. تتغير الأعداد الفعلية مع زمن الاستجابة وحالة الصفحة والأخطاء. المستخدم غير المسجل ليس مشمولًا بهذا السيناريو.
- اختبرت الدالة الأصلية داخل Node VM مع اتصال Ably وهمي سليم وبدون SSE: سجلت مؤقتين بفاصل15000ms. ومع SSE OPEN أصبحا60000ms. هذا إثبات سلوك وليس اختبار متصفح إنتاجي.

**التأثير المؤكد:** استمرار توليد الطلبات في حالة كان يمكن فيها الاعتماد على الإشعارات اللحظية/المصالحة المحدودة بدل إعادة تحميل دوري واسع. مقدار CPU المدفوع لكل طلب غير مقاس.

## 2. تحديث profile ليس طلبًا منفردًا — مثبت في مسار النجاح

الدليل: [app.js L1953–2045](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/app.js#L1953-L2045).

نجاح `/api/user/profile` يستدعي:

- `loadGameHistory()`، الذي يجلب `/api/games/history` إذا كان العنصر موجودًا.
- `startNotificationPolling()`، الذي يجلب `/api/notifications` فورًا، ثم يعيد جدولة المؤقتين.
- `loadHomeSummary()`، الذي يجلب `/api/user/home-summary`.
- `loadReferralRewardHistory()`، الذي يجلب سجل مكافآت الإحالة عند وجود عناصر العرض.
- `loadCpaLeadOfferwall()`، الذي يجلب رابط العرض ويضبط iframe.src عند نجاحه ووجود عناصره.
- `loadAccountGrowth()`، الذي يجلب `/api/user/growth` عند تحقق شروطه.

إذًا لا يصح عد مؤقت profile على أنه قراءة صغيرة واحدة. توجد طلبات فرعية تتكرر حتى إن المستخدم لا يشاهد تبويباتها، بحسب وجود العناصر فيDOM. إعادة ضبط iframe قد تضيف تحميلًا خارجيًا، ولا أنسب معالجته الخارجية إلىCPU Vercel.

**توضيح مهم:** لم أثبت تسربًا غير محدود للمؤقتات؛ الاختبار يثبت أن الدالة تلغي القديم قبل إضافة الجديد. توجد أيضًا حماية `profileRequestInFlight` تمنع تراكب profile نفسه. المشكلة المثبتة هي تكرار العمل واتساعه، لا اختراع حلقة لا نهائية.

## 3. الطلب المتكرر مكلف في طبقة البيانات — مثبت بنيويًا

الدليل: [auth.js L25–59](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/src/middlewares/auth.js#L25-L59)، [userController.js L22–43](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/src/controllers/userController.js#L22-L43)، [dataAccess.js](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/src/services/dataAccess.js).

- middleware يفحصJWT والجلسة ويقرأ المستخدم.
- handler الخاص بالـprofile يعيد قراءة المستخدم نفسه، ثم يجلب حتى3 مستويات إحالة، ويحسب فرقًا وإحصاءات ويستدعي `syncGameCredits()`.
- في مسارSupabase، `supabaseFindOne('users',...)` يطلب أيضًا `wallet_balances`؛ تكرار قراءة المستخدم قد يعني أكثر من طلب شبكة، لاSELECT واحدًا.
- مسار سجل مكافآت الإحالة يطلب حتى10000 صف ويحسب المجموع فيNode؛ هذا سقف الطلب البرمجي وليس دليل أن10000 صف يرجع فعليًا لكل مستخدم.

**لا توصية بإلغاء المصادقة أو فحص الحظر/الجلسة أو cache رصيد مالي عامًا.** التحسين الممكن هو إعادة استخدام بيانات موثوقة داخل الطلب نفسه، وفصل تجميع الإحصاءات عن كل مزامنة profile، واستبدال تنزيل سجلات كبيرة بتجميع/صفحات مدروسة. أي تغيير يمس مكافآت أو أرصدة يحتاج مراجعة واختبارات مستقلة.

انتظارSupabase ليس مساويًا لكل مدةActive CPU؛ العائد من تقليل الطلبات يشمل تقليل تحليل JSON/التجميع/الاستدعاءات، لكن لا نستخرج تكلفته منwall-clock وحده.

## 4. الملفات الثابتة تمر في وظيفة Node — مثبت من إعداد الإنتاج

الدليل: [vercel.json](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/vercel.json)، [src/app.js L349–448](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/src/app.js#L349-L448).

- build واحد `server.js` عبر`@vercel/node`، والمسار`/(.*)` يوجه إليه.
- HTML/JS/CSS/صور/خطوط وفيديو ضمنincludeFiles؛ Express يخدم الملفات عبرsendFile وexpress.static.
- JS/CSS تحملno-cache/revalidation، وصفحةالتطبيقno-store، وخدمةstatic العامةmaxAge:0.
- الـservice worker يتبعnetwork-first، وليسcache-first للأصول، ويمنعcache API، وهو صحيح للبيانات المالية لكنه يزيد أهمية فصلالأصولالعامة عنوظيفةAPI.

هذه البنية تدخل طلبات الأصول العامة إلى وظيفة التطبيق حسب قواعد التوجيه والتخزين الفعلية، بدل أصل static مستقل في النشر. لا يعني مرور الطلب أن CPU يعادل حجم الملف أو مدة النقل؛ لم تُقَس نسبة إصابة CDN أو عدد الاستدعاءات.

الإصلاح المقترح: فصل الأصول العامة المبصومة إلى static/CDN مع استثناء مسارات الإدارة والحساب والـAPI صراحة. **لا تحويل كل HTML إلى cache عام، ولا إلغاء CSP أو بوابة admin.**

## 5. جدولة خارجية مزدوجة للتذكير — مثبتة، مع دليل تشغيل

الدليل: [عامل البث](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/.github/workflows/admin-email-broadcast-worker.yml) و[عامل التذكير](https://github.com/semoheva123/OPX/blob/c33055f12cdc49053417f06183ca8e22bde9c039/.github/workflows/email-verification-reminder-worker.yml).

- كلا العاملين يطلب `process-email-verification-reminders`، وكل منهما مضبوط على `*/5 * * * *`، ومجموعتا concurrency مختلفتان.
- API GitHub أظهرهما active، وأظهر تشغيلًا مجدولًا ناجحًا لكل منهما يوم5 نوفمبر: [broadcast42006293724](https://github.com/semoheva123/OPX/actions/runs/42006293724) و[reminder41996430404](https://github.com/semoheva123/OPX/actions/runs/41996430404).

- لا أساوي جدولة كل5 دقائق بتنفيذ فعلي288 مرة يوميًا؛ عينة التشغيل المسترجعة تظهر فواصل أطول. لا عدد فاتورة دقيق مستنتج من cron expression.
- العامل المالي أيضًا active، وأحدث تشغيل [42006248933](https://github.com/semoheva123/OPX/actions/runs/42006248933) فشل في خطوة `Validate financial schema before processing queues` وفق jobs API. لم تتوفر سجلات الخطوة بسبب فشل جلب مضيف السجلات؛ سبب فشل التحقق التفصيلي غير معلوم. لا أنسب الفشل إلى ضغط CPU، ولا أشغل payout أو repair لاختباره.

## 6. عيب cache HTML إضافي — مثبت محليًا، وليس سبب CPU رئيسيًا مثبتًا

في `renderIndexHtml()` تحفظ الدالة `renderedIndex.html` كنص، لكنها في النداء التالي ترجع `renderedIndex.html.html`، أي undefined. أكد اختبار المقتطف الأصلي أن الأول نص والثاني undefined. يرجع `sendAppHtml()` عندها إلى sendFile؛ **هذا لا يثبت صفحة فارغة**، لكنه يلغي مسار القالب المخزن في الطلبات التالية ويؤثر على حقن build metadata. حجم الأثر على CPU غير مقاس.

## الاختبارات المنفذة

ملف إثبات محلي: `/home/user/opx-cpu-audit/prove.mjs`، الأمر: `node /home/user/opx-cpu-audit/prove.mjs`.

خمس حالات PASS:
1. Ably سليم لا يبطئ polling: مؤقتان15000ms.
2. SSE OPEN يبطئ المؤقتين إلى60000ms.
3. إعادة startNotificationPolling تجلب الإشعارات فورًا ولا تزيد المؤقتين عن اثنين.
4. تبويب مخفي يتخطى callback جلب الإشعارات.
5. HTML cache يرجع undefined في المرة الثانية مع وجود fallback.

لا تطبيق قيد التشغيل، ولا قاعدة بيانات، ولا فك أسرار، ولا طلب production أُرسل بهذه الاختبارات. هذه ليست benchmarks لـActive CPU ولا اختبارات جهاز حقيقي.

## ترتيب المعالجة المقترح — غير منفذ

1. إصلاح قرار مزامنة الواجهة: حالة Ably/SSE وstandalone، والاستغناء عن polling المالي بإشعارات مع مصالحة snapshot آمنة عند الاتصال/العودة/الفجوة؛ لا تكرار صامت واسع، ولا تفويت تغييرات أو إزالة حواجز التحقق.
2. فصل تحميل profile الأساسي عن تحميل السجلات والإحصاءات والـiframe، وتحميل الثانوي عند فتح التبويب أو وصول حدث متعلق به. إعادة استخدام قراءة المستخدم داخل الطلب نفسه بعد المصادقة دون إلغاء فحوص الصلاحية.
3. فصل الأصول العامة المبصومة عن وظيفة Express، مع اختبار منع كشف admin والملفات الخاصة وحفظ CSP والنطاق.
4. توحيد ملكية عامل تذكير البريد بعد مراجعة الأقفال والصفوف المعلقة؛ لا تعطيل للعمل المالي أو البريدي بلا خطة تسليم.
5. إصلاح cache HTML باختبار regression، ثم قياس فترة متقابلة قبل وبعد.

## ما يلزم لإغلاق السبب الكمي بثقة

من Vercel، لنفس فترة الفوترة: توزيع Active CPU وعدد invocations حسب function/route والـenvironment، ومعدل الخطأ والـcache hits وعدد الزيارات. نحتاج خصوصًا profile/notifications/home-summary/referral-rewards/growth/static/cron. إن كانت كل المسارات تحت server.js واحدة، يلزم ربط request logs بالمسارات ومؤشرات CPU على النافذة، أو instrumentation محدود بعد إذن؛ `durationMs` الموجود حاليًا يقيس زمن الطلب لا CPU.

لا يدعم موصل Vercel الحالي قراءة هذه المقاييس. لذلك الاستنتاج الدقيق هو: **وجدنا أسباب عمل زائد حقيقية في كود الإنتاج وأثبتنا سلوك بعضها محليًا؛ لم نثبت أي مسار استحوذ على معظم ساعتين25 دقيقة، ولا أن النقل وحده سيحلها.**
