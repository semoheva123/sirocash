# Demand-based TRON funding + energy + withdrawal planner

`planTronFunding` composes the USDT gross-deducted tariff (5 USDT), operating-liquidity checks, economical sweep selection, energy-gap package planning, ambiguous transaction reconciliation and final settlement decisions. It rents to the actual sender: the deposit address for a sweep, the operating address for a payout. No sweep if net payout liquidity is already sufficient. A partial sweep only covers the shortage or one source's spendable balance; workers must re-read finalized state before another step.

Test sequence: gross20/net15 -> operating5 -> energy for source -> sweep10 -> pending tx reconciliation -> operating15 -> energy for operating sender -> prepare payout15 -> reconcile payout -> settle. Cases cover blocked price caps, stale evidence, missing device approval/reservations and insufficient native gas/bandwidth. Tests are synthetic. No funds or API calls.

## Hard boundary

This is a deterministic PRIVATE PLANNER, not a deployed dispatch worker and not proof of actual finality. No frontend route calls it. No store claims, signed transactions, provider purchases or ledger settlements are performed. Action keys fingerprint exact intent but do not by themselves prevent double execution. Pending transaction IDs must come from durable records; finality from independent verified receipts, not customer flags. `fundingReservedForOperation` means trusted atomic treasury allocation; it cannot be supplied by a user.

A production worker must atomically claim sender resources/budgets and persist immutable intent/action keys, bind exact quote package/sender/price/duration and energy-order IDs, enforce price caps on purchase, independently verify delivered resources, then persist signed transaction identity BEFORE broadcast. Never create a replacement key after an unknown result. Quote freshness and delegation window must be rechecked at execution. Operator caps on total sweep/native costs and signer allowlists remain required; economical/spendable/resource fields are trusted inputs, not computed chain evidence here. Revalidate max total cost across multiple sources, not merely per rental. Final settlement must bind exact recipient/net amount/transaction ID and atomically post gross debit, net settlement and platform fee. Reject/failure network-cost treatment still needs explicit policy.

TronBid remains a candidate for the adapter, not a funded or approved live provider. Its price-cap behavior/API eligibility and service reliability must be verified. Existing quote and rental-intent modules do not implement payment or fallback. No claim that it is currently cheapest. Isolated signer, authenticated RPC watcher, persistent approval, restricted database permissions and real funded/concurrency tests remain mandatory. Existing live-finance guard is unchanged.
