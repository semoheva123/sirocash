# خطة نقل SiroCash إلى حساب Vercel مستقل

**الحالة: خطة فقط — 5 نوفمبر 2026. لا إنشاء حساب، ولا نقل، ولا تغيير نطاق أو أسرار أو مهام.**

## 1. شروط البدء والحدود

- الحصول على تأكيد Vercel بأن نقل هذا المشروع إلى الحساب الجديد مسموح في هذه الحالة، وأن خطة الوجهة تسمح بطبيعة استعمال المحفظة. النقل ليس إجراءً لإعادة ضبط الحصة أو تجاوز الإيقاف، ولا يُفترض انتقال الاستثناء المؤقت 3×.
- يجهّز المالك حساب الوجهة ويؤمّنه بمصادقة متعددة العوامل، ثم يربطه عبر اتصال Vercel الرسمي في Arena. لا تُرسل كلمات مرور أو رموز دخول أو مفاتيح خاصة في المحادثة.
- قراءة الفرق والمشاريع المتاحة لاكتشاف وجهة النقل ومعرّفاتها الفعلية، ثم أخذ موافقة على الوجهة بالاسم. لا افتراض أن الاتصال الحالي يملك صلاحيات الحساب الجديد.
- لا شراء اشتراك أو إنشاء مشروع مدفوع أو ترقية أو تغيير مزوّد. لا نقل مشاريع opx أو waleed-forex.
- صور الاستخدام المعروضة أظهرت للمحفظة 2h27m، ولـopx مقدار 2h25m في الفترة المعروضة؛ هذا ليس قياسًا للمعدل المستقبلي ولا تحديدًا لمسار CPU المسبّب. يلزم قياس استهلاك المحفظة مستقلًا قبل النقل وبعده.

## 2. الجرد قبل أي كتابة

يُجمع جرد خاص بالمشروع، دون طباعة قيم الأسرار أو وثائق العملاء:

| العنصر | ما يلزم تسجيله والتحقق منه |
|---|---|
| إصدار التطبيق | SHA الإنتاج الفعلي، حالة النشر، إصدار الرجوع؛ لا اعتبار آخر دمج منشورًا تلقائيًا |
| البناء | Node.js 22 وفق package.json، أوامر البناء والتثبيت، حدود الذاكرة والمدة والمناطق |
| النطاق | www.sirocash.online كنطاق قانوني أساسي، sirocash.online وإعادة توجيهه، TLS وسجلات التحقق |
| إعدادات البيئة | أسماء المتغيرات، النوع، نطاق production/preview، مصدر الحفظ الآمن، ومالك كل سر — لا قيم في الجرد |
| الوصول | صلاحيات GitHub وVercel وحماية المعاينات والنشر التلقائي وهوية OIDC وأي قيود مرتبطة بمعرّف الفريق/المشروع |
| المهام | Vercel Cron، Supabase pg_cron/pg_net/Vault، GitHub Actions، webhooks وأي مراقب أو مصدر HTTP خارجي |
| حالة المال | المراجع والحالات للطلبات الجارية والحجوزات ونتائج الإرسال غير المؤكدة، مع حماية خصوصية العملاء |
| الاستهلاك | Active CPU والاستدعاءات حسب المسار والفترة، ميزانية الخطة الجديدة، وحدود اتصالات PostgreSQL أثناء الانتقال |

مصادر الجرد الموجودة في المستودع: vercel.json، docs/production-canonical-domain.md، docs/identity-cloudflare.md، docs/web-push-pwa-search.md، docs/deposit-monitor-scheduler.md، وملفات سير العمل في .github/workflows.

## 3. ما يبقى في مكانه

الاقتراح الأول هو نقل الاستضافة فقط، دون نقل البيانات أو إنشاء بدائل لها:

- قاعدة Supabase الحالية، الحسابات، الأرصدة، السجل، الحجوزات، UID والجلسات ومفاتيح المرور المسجّلة.
- Cloudflare Worker وD1 الخاصان بالهوية، مع الحفاظ على صلاحيات الوثائق وسياسة الاحتفاظ.
- خدمة البريد ومفاتيح Web Push الحالية لتجنّب إبطال الاشتراكات دون داعٍ.
- النطاق الأساسي نفسه. لا تغيير WEBAUTHN_ORIGIN أو RP ID إلى عنوان vercel.app الجديد.
- مفاتيح الحفظ المالي والعناوين والمسارات الاشتقاقية والسياسات والرسوم والميزانيات التشغيلية تبقى كما هي. لا تدويرها ضمن نقل الاستضافة ولا تنفيذ تحويل تجريبي حقيقي دون إذن مستقل.

**مهم للهوية:** لا تغيير IDENTITY_SUBJECT_SECRET؛ تغييره يفصل المعرّفات المستعارة عن الوثائق الموجودة وقد يجعل المصالحة تتعامل معها على نحو خاطئ. تبقى مهام دورة الحياة في الوجهة متوقفة حتى التحقق من السر نفسه وقاعدة الحسابات نفسها.

الأسرار غير القابلة للتصدير تحتاج إعادة إدخال من مخزن المالك الآمن، لا استخراجها في سجلات أو ملفات Git. نقص أي سر مطلوب يوقف الانتقال بدل توليد بديل تلقائيًا.

## 4. اختيار آلية النقل

**الأفضل تقييم النقل الرسمي للمشروع نفسه بين الفريقين أولًا** إذا أكد Vercel توفره وأثره على النطاقات والأسرار والسجلات والمعاينات والمهام. لا نفترض أن جميع الإعدادات تنتقل أو أن النقل الرسمي يضمن عدم الانقطاع.

إذا لم يتوفر وكان Vercel يسمح بإنشاء مشروع بديل للحساب المستقل:

1. إنشاء وجهة واحدة فقط بعد الموافقة، وبناء إصدار محدد تم اختباره.
2. البدء ببيئة معزولة بلا بيانات عملاء ولا مفاتيح مالية ولا اشتراكات دفع أو مهام إنتاجية.
3. عدم ربط معاينات Git بقاعدة الإنتاج أو بيانات الهوية الحقيقية. الربط المحدود بالإنتاج يكون في نافذة الانتقال وبصلاحيات ضرورية فقط.
4. لا إيقاظ تلقائي للعمال أو تفعيل أي خدمة كانت معطّلة أصلًا. نقل قيم أعلام التفعيل المعتمدة بدقة، لا جعلها جميعًا true.
5. لا نشر مالي على عنوان مؤقت بتغيير أصل WebAuthn؛ اختبارات الحساب والجهاز النهائية بعد ربط النطاق القانوني.

## 5. منع التشغيل المزدوج — شرط حاسم

تعطيل مهمة Cron في مشروع الوجهة وحده لا يكفي؛ قد تأتي الطلبات من Supabase أو GitHub أو عناوين نشر قديمة. كما أن تعديل متغيرات البيئة لا يعدّل النشرات القديمة القائمة.

قبل إتاحة الكتابة من الوجهة:

- حصر كل منتج ومنفّذ للمهام: اكتشاف الإيداعات، التسوية، التجميع، الدفع، الموارد، إشعارات Push، دورة حياة الهوية والمصادر الخارجية.
- إيقاف المنتج القديم أو تغيير هدفه مرة واحدة وفق جرد محدد، بعد حفظ حالته. لا حذف صفوف الطوابير أو مؤشرات المسح.
- منع التنفيذ والكتابة من المشروع القديم **على مستوى يغطّي النشرات السابقة والعناوين المباشرة**، والتحقق فعليًا من المنع. إذا استُخدم إيقاف المشروع، يجب التحقق من مداه وإمكان الرجوع قبل الاعتماد عليه؛ DNS وحده ليس حاجزًا.
- إذا تعذّر ضمان كاتب واحد بالآليات الموجودة، يتوقف النقل. أي قفل/حاجز ملكية جديد في قاعدة البيانات يحتاج تصميمًا واختبارًا وموافقة مستقلة على الترحيل.
- ترك العمليات الجارية تنتهي أو تسجيلها كغير مؤكدة؛ لا إعادة بث أو إنشاء طلب بديل أو تحرير حجز مجهول النتيجة.
- تشغيل مالك واحد لكل وظيفة على الوجهة، مع بقاء مفاتيح عدم التكرار والأقفال وحدود الميزانيات المشتركة في قاعدة البيانات.

## 6. نافذة الانتقال

1. إعلان نافذة صيانة قصيرة متفق عليها. لا وعد بانعدام الانقطاع.
2. تأكيد نسخة احتياطية قابلة للاسترجاع وصلاحيات الوصول إليها دون نسخها إلى Git. النسخة الاحتياطية ليست مبررًا لرجوع قاعدة بيانات مالية إلى الماضي.
3. تثبيت SHA الإصدار وإيقاف النشر التلقائي غير المنسّق في الجهتين مؤقتًا.
4. تأكيد عدم وجود عمليتين متوازيتين، وإيقاف الكتابة المالية الحساسة أثناء التسليم بآلية مختبرة. إذا لم تتوفر آلية توقف آمن، لا يبدأ النقل.
5. نقل النطاق/إثبات ملكيته وفق آلية Vercel المعتمدة. لا تغيير nameservers ولا MX/SPF/DKIM/DMARC أو DNS غير المرتبط بالمشروع، إلا إن ثبت لزومه وحصلت موافقة مستقلة.
6. التحقق من TLS للنطاقين والتحويل إلى www ومن نجاح الطلبات على الاستضافة الجديدة، لا الاعتماد على READY وحدها.
7. نقل أهداف المهام والأسرار التشغيلية اللازمة بأمان، ثم تشغيل وظيفة واحدة في كل مرة بعد قبولها، دون نسخ جداول Cron أو إنشاء أسرار مكررة.
8. مراقبة الأخطاء وCPU وعدد الاستدعاءات ومؤشرات المسح والطوابير خلال أول ساعة ثم خلال 24 ساعة. نقاط القياس ليست ضمان استجابة على الأجهزة الحقيقية.

## 7. اختبارات القبول

- تحميل الصفحات العربية/الإنجليزية على الهاتف، TLS، إعادة توجيه النطاق، وعدم وجود اتصالات متصفح إلى localhost أو أصل قديم خاطئ.
- دخول حساب اختباري مأذون، جلسة موجودة إن أمكن، وعزل الحسابات. عدم استخدام جلسات العملاء في الاختبارات.
- مفتاح مرور فعلي على النطاق الأساسي بموافقة صاحب حساب الاختبار؛ فشل النطاق المزيف أو المعاينة غير المصرّح بها. لا طلب PIN أو بصمة من المالك داخل المحادثة.
- قراءات الرصيد والحجوزات والمراجع متسقة، ولا تغييرات على الأرصدة. اختبار تنفيذ مالي حقيقي يحتاج موافقة مستقلة؛ لا تدّعي هذه الخطة أنه تم.
- تحديثات SSE وإعادة الاتصال المحدودة دون حلقة polling جديدة، واستمرار الضوابط عند غياب الشبكة أو غموض النتيجة.
- إشعار اختباري غير مالي لمشترك مأذون: قبول خدمة Push ليس إثبات وصول للهاتف.
- فحص هوية اصطناعي فقط، عزل المالك، MFA للمراجع، منع الموافقة الذاتية والحذف. الفحص المنشور الحالي له آثار اصطناعية ومصالحة حقيقية وحصة AI؛ لا تشغيله من بيئتين متوازيتين، ولا تجاوز سقفه أو تعطيل شرط الجاهزية لتنجح عملية النشر.
- تأكيد بقاء الوظائف غير المفعّلة معطّلة، وعدم تكرار dispatch أو إشعارات أو جدولة أو تحليل وثائق قديمة.

## 8. الرجوع عند الفشل

أسباب الرجوع: تعطل الأصل/TLS، عدم اكتمال نقل الأسرار، فشل الجهاز أو العزل، ازدواج عمال، قراءات مالية غير متسقة، أو استهلاك غير مضبوط.

- تعطيل الكاتب والمهام في الوجهة أولًا، وحفظ المراجع الجديدة والحالات الجارية؛ لا إعادة محاولة مالية تلقائية.
- إعادة النطاق/التوجيه والإصدار المقبول السابق وإثبات مالك واحد للمهام قبل استئنافها.
- استخدام **قاعدة البيانات الحالية**؛ لا استعادة لقطة قديمة لمحو معاملات تمت بعد الانتقال.
- إذا تعذّر الرجوع الآمن أو كانت نتيجة إرسال مالي مجهولة، إبقاء الخدمة في صيانة مع عرض الحالة الصادقة حتى المصالحة.
- لا حذف المشروع القديم أو إلغاء مفاتيحه أثناء نافذة الرجوع. بعد قبول التشغيل، تُراجع صلاحياته وحماية أسراره ويُؤرشف/يُزال بإذن منفصل؛ لا يظل منفذ تنفيذ مالي قديم نشطًا.

## 9. قرار Go / No-Go

لا يبدأ النقل ما لم تُستوفَ كلها:

- [ ] موافقة Vercel على النقل ومناسبة خطة الاستخدام.
- [ ] حساب وجهة مؤمّن ومربوط رسميًا، ومعرّفات وأذونات معروفة.
- [ ] جرد المصدر والإصدار المنشور فعليًا، والأسرار دون كشف قيمها.
- [ ] تحديد أثر النقل على نطاقات ومعاينات Vercel القديمة.
- [ ] خطة توقف/منع كاتبين مختبرة وخطة رجوع قابلة للتنفيذ.
- [ ] بقاء Supabase وD1 وRP ID والبيانات المالية ثابتة.
- [ ] اكتمال اختبارات القبول وحدود الاستهلاك والتنبيهات المتاحة.
- [ ] موافقة المالك على نافذة التنفيذ والموارد والتكاليف إن وجدت.

**المخرَج الحالي:** وثيقة تخطيط مبنية على المستودع والسياق المتاح فقط. لم تُفحص وجهة جديدة أو تُثبت صلاحياتها أو جاهزيتها، ولم يُنفّذ أي نقل. لا تعد هذه الوثيقة موافقة من المزوّد أو ضمانًا لاستمرار المجانية.
